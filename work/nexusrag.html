01 — OverviewNot another chat wrapper.

Most “chat with your PDFs” demos embed chunks, grab the nearest few and hope. That fails on exact terms — product codes, clause numbers, names — and it fails silently, with a confident answer and no way to check it. NexusRAG treats retrieval as the product: two retrievers in parallel, principled fusion, explicit evidence selection, and an abstention gate before any token is generated.

50 + 50lexical and dense candidates per query
25 → 10after fusion, then re-ranking
4LLM providers in a failover chain
8input formats, up to 50 MB each
160automated tests
~25Klines of Python across 9 layers

02 — The pipelineFrom raw files to cited answers.

One Postgres database holds both indexes, so a hybrid query is two SQL statements, not two systems.

Why both retrievers

Dense vectors understand that “termination” and “ending the contract” are related; full-text search knows that Clause 14.2(b) means exactly that. Running both and fusing by rank — not by raw score, which isn't comparable across retrievers — gets the strengths of each. The same idea, with a MiniLM transformer re-ranking BM25F and Word2Vec/FAISS candidates 50 → 10, powers my earlier biomedical search engine over PubMed.

03 — Layered designNine layers. Imports only flow down.

L0–L1Core types and typed contracts — every embedder, retriever, reranker, parser and LLM sits behind an interface.
L2Domain logic — chunking strategies, retrieval, fusion, filters, evidence, abstention, citations.
L3Flows — ingestion and query orchestration with per-stage latency diagnostics.
L4Providers — PyMuPDF, Postgres/pgvector, SQLite FTS5 + Qdrant, LLM APIs.
L5–L6Wiring and security — dependency injection, rate limiting, auth.
L7–L8Interfaces and runtime — FastAPI, a Typer CLI, sync/async SDKs, the Next.js workspace.

04 — Key decisionsChoices that make it trustworthy.

01

Abstain instead of hallucinate

If there isn't at least one evidence passage above 0.3, with a mean above 0.4, the system says so. A grounding check (≥ 0.5) and a citation validator run after generation too.

02

Failover as a state machine

Gemini 2.5 Flash → GPT-4.1 mini → Claude Sonnet → Llama 3.3 70B on Groq. Three retries with exponential backoff and jitter; after three consecutive failures a provider cools down for 60–300 s.

03

One codebase, two deployment modes

Set DATABASE_URL and it runs on Postgres + pgvector; leave it empty and it runs locally on SQLite FTS5 + Qdrant. Same tests, same API.

04

Observability per stage

Every query records latency for each stage — retrieval, fusion, filtering, re-rank, generation — so regressions show up as numbers, not complaints.

05

A safe public demo

The hosted version gives each visitor two free questions, tracked server-side, then asks them to bring their own key.

05 — The productA workspace, not a chat box.

Deployed with the frontend on Cloudflare Pages, the API on Koyeb and the database on Neon Postgres.

06 — What's nextMeasured, not claimed.

  • Model-backed adapters. The open-source build ships lightweight deterministic embedder and reranker adapters so it runs anywhere; a sentence-transformer embedder and a cross-encoder reranker are the next adapters behind the same interfaces.
  • Evaluation harness. Publish recall@k, nDCG and faithfulness on a public benchmark for each configuration.
  • Conversation memory. Server-side session memory for follow-up questions.
