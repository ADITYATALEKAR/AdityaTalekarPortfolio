00 — ContextA live site with untrustworthy numbers.

Exactitude Consultancy publishes around 30,000 industry reports. When I joined as the sole engineer for data, AI and infrastructure, four problems were hurting the business at once:

01

Stale, inconsistent figures

Wrong units, impossible growth rates and placeholder company lists across thousands of reports.

02

Slow pages

The homepage took close to a second to load.

03

Silent failures

Enquiry e-mails were failing without any error — leads saved, nobody notified.

04

Everything manual

Content and lead handling were done entirely by hand.

Constraint

A near-zero budget for paid APIs. Every solution had to be cheap to run — and safe to apply on a production site that real customers were using.

03 — Case study 1Agentic design: Python does the work, AI finishes it.

Sending 30,000 reports to an AI model one by one would have been slow, expensive and impossible to audit. Instead I split every job into small steps and gave each step to the cheapest tool that could do it reliably.

Python handles the bulk of decisions; AI is reserved for judgement calls, and never gets the final word alone.

  • Python does the deterministic work: crawling research firms' public sitemaps (about 1 million report pages), matching pages to our reports by exact market name and region, pulling figures out with regular expressions, converting everything to US dollars while catching million/billion mix-ups, and computing a consensus across sources.
  • AI handles only judgement calls: “Is this headline really about this market?” and “Is this figure plausible for this product?”
  • Two different models must agree before a large change goes live, and a third model checks separate random samples.
  • Python applies the result safely: backup → write → render check of live pages → automatic rollback if anything breaks.
Decisions needing an AI call100%~5%

Most of that AI work ran on free tiers, and about 22,000 corrections went live — every one traceable to its sources.

What I learned

Neither the free models nor a mid-tier model working from memory were reliable referees on their own — both made confident mistakes in both directions. What worked was independent sources agreeing, plus web-search agents that must cite a page, which Python then fetches and checks.

04 — Case study 2Verifying market data at scale.

01

A strict same-market matcher

“Spine surgery robots” is not “spine surgery”; “online gambling” is not “gambling”. Near-misses are rejected, not rounded up.

02

Source tiers

Established firms, smaller firms and mass-produced sites are weighted differently. Mass-produced sites can confirm a figure but never decide one alone.

03

Typo protection

Any figure more than 5× away from the median of the other published figures is dropped as a likely typo — one firm had printed a “USD 4,500B” market for a niche device.

04

Accountability

Every change is written to a ledger with its source URLs, and any batch can be rolled back.

Scaling the search

DuckDuckGo started refusing our GitHub runners. I traced it to query length — queries over ~120 characters were rejected — capped them, made workers skip a refused query instead of stopping, and scaled out to 12 runners.

Time to search 1,057 reports4+ hours~15 min

The result: 48.9% of reports are now cross-checked to within ±25% of published research.

06 — Case study 4Edge caching: 909 ms → 1 ms.

Problem. Pages took up to ~900 ms to load, even though a page cache was supposedly set up.

Diagnosis. The cache had never actually worked. PHP session headers on every page were telling Apache not to cache anything.

Fix. I removed session handling from public pages, configured Apache's disk cache properly, and sent correct cache headers so Cloudflare could cache at the edge too.

Homepage response time909 ms1 ms
Report page response time243 ms4 ms
Lesson

Measure before adding hardware. The bottleneck was a configuration detail, not server capacity.

07 — Case study 5The month the enquiry e-mails went silent.

Symptom. For about a month, enquiry e-mails never arrived. Leads were saved, but nobody was notified — about 70 enquiries were affected.

Root cause. The mail code sent each message by calling the site's own public URL. Cloudflare's bot protection challenged that server-to-itself request, so every send failed without an error.

The fix

  • Send directly over authenticated SMTP, with TLS verification on.
  • A delivery log for every message.
  • Automatic confirmation e-mails to visitors.
  • Request IDs and a public “track your request” page.
  • An e-mail validity check on the form.
  • The old relay endpoint closed for good.
Lesson

A CDN's security layer can break your own internal calls. Internal services should never route through the public edge.

08 — Case study 6Handling the bot attack.

The production server was a small 2-core machine, and it was being hammered by AI scrapers, aggressive SEO crawlers and automated vulnerability scanners. Cloudflare analytics showed the scale of it, so I moved the defence to the edge:

  • Custom Cloudflare WAF rules for known-bad patterns and automated scanners.
  • User-agent blocks for scrapers and aggressive crawlers — the site now refuses them outright.
  • Rate limiting and request timeouts.
17.6Mrequests in a 48-hour window
1.35Mthreat-flagged and blocked at the edge (8%)
2 coreson the origin server — so the edge had to do the work
Lesson

A small origin can't out-compute automated traffic. Stop it at the edge, before it costs you anything.

09 — Case study 7Web-search cost: an estimated $24,000+ → $0.

01

No paid search for research-firm pages

I read their public sitemaps directly — finding about 1 million pages needed no search API at all.

02

Free searching for the rest

Remaining searches ran on GitHub Actions' free runners, at a gentle, rate-limited pace.

03

AI search only where it adds value

The AI web-search agent ran on a flat-rate plan, and only for the cases the free pipeline couldn't solve.

04

News collected in public

Company and industry news is gathered in a public GitHub repository and imported by the server — so the server never queries Google itself.

10 — Case study 8An agentic content and lead pipeline — with a human in charge.

Every week the pipeline runs end to end in about 6.5 minutes:

  1. Collect signals — news, Search Console queries and search suggestions.
  2. Pick topics worth writing about.
  3. Build verified fact sheets.
  4. Draft blogs, press releases, FAQs and keyword headings.

Python templates do most of the writing; AI writes only short narrative paragraphs. Nothing goes live without a person approving it in the admin panel, and strict limits on keyword changes per report, per week and per month prevent over-optimisation.

Admin access control I built

  • Full or custom roles across 13 sections, each set to none, view or edit.
  • bcrypt password storage and an audit log.
  • A guard that runs before every admin page and fails closed.
  • 42 automated tests.

I also designed and costed an AI proposal-writing agent at about $3.49 per researched proposal.

11 — Lessons learnedWhat I'd tell the next engineer.

01

Make AI cite its evidence, then check it in code

Trust comes from verification, not from the model.

02

Deterministic code first, AI last

It's cheaper, faster and auditable.

03

Every bulk change needs a backup, a render check and a one-command rollback

On a live site, these saved me more than once.

04

Measure before optimising

The 900 ms problem was one configuration detail.

05

Write postmortems

Several of my fixes came from understanding exactly why something failed.

12 — What's nextWhere I'd take it.

  • Replace planning estimates with measured cost and quality metrics for every AI step.
  • Add official statistics — trade data and national statistics — as a further cross-check for market sizes.
  • Move the proposal agent from design to production, with a quality trial against human-written proposals.
