Wave Engine

A local-first AI engineering partner for VS Code that reads your repository before it answers — and checks its own work before you see it.

107specialist agents
767Marketplace downloads
~40s→5sresponse time
Full case study Marketplace
Problem
AI coding assistants guess when they can’t see your repository, and most send your code to a third-party cloud. Developers get plausible answers with no evidence and no control.
Approach
Flip the architecture: deterministic agents gather evidence from the repo (files, imports, tests, architecture), an answer-critic lists what a correct answer must include, and only then does a 3-billion-parameter model running 4-bit on the user’s own CPU write the answer — which is scored and regenerated if weak.
Why it works
A small model that only has to explain evidence it was handed — and is graded before it speaks — is far more reliable than the same model answering from memory. The intelligence lives in the system, not the weights.
  • Runtime: VS Code extension (TypeScript) → FastAPI backend on 127.0.0.1 with 157 routes; a bundled llama.cpp server runs Qwen2.5-Coder-3B (Q4_K_M, 1.9 GB) with 8-bit KV cache; context and slots adapt to free RAM (32K/3 → 8K/1).
  • Orchestration: a blackboard with capability bidding (max 5 bidders; utility = capability × load × reliability) runs a staged pipeline — repo map → rule checks → memory → hypothesis → causal analysis → repair plan → verify → deep read → architecture trace → tests → memory store.
  • Self-correction: 2–3 parallel reasoning chains with different evidence strategies; a confidence scorer picks the winner and re-scores it on relevance, completeness and specificity — below 0.55 it regenerates with the critic’s feedback.
  • Code generation: a 5-agent council (Architect → CodeGen → Tester → Reviewer → Optimizer) approves only at consensus ≥ 0.7, then a generate → run → fix loop feeds exact errors back to the model.
  • Latency: SQLite answer cache keyed by SHA-256 of prompt + repo state with fuzzy matching (Jaccard ≥ 0.82); byte-identical system prefix for KV reuse; n-gram speculative decoding.
  • Safety: grammar-constrained tool calls (GBNF), loop stops on a repeated error hash or 15 iterations; writes, shell and network need approval; path-traversal and secret-leak guards.
  • Scale: 107 agents (17 core Python classes + 5 council + 85 declared in Markdown/YAML), ~108K lines of Python, 864 tests, 48 VS Code commands.
  • Live on the VS Code Marketplace since March 2026 under the Fundamental Labs publisher: 767 downloads, 30+ active users, 106 updates, now v4.6.
  • Typical response time on CPU went from ~40 seconds to ~5 seconds after the caching work.
  • Works fully offline with no API key — the user’s code never leaves the machine unless they choose a cloud model.
  • Grew beyond coding into a local “Life OS”: morning briefings across calendar, e-mail and GitHub, cross-repo search, a DevOps dashboard and a secret scanner.

Guardian

External attack-surface intelligence for banks — see your infrastructure the way an attacker does, and find the weak points first.

44discovery modules
960node trust graph
6m 43sfull scan cycle
Full case study
Problem
Banks run thousands of internet-facing endpoints that change weekly. Expired certificates, weak ciphers, forgotten subdomains and quantum-vulnerable keys are usually found by a breach or an auditor, and traditional scanners lose cycle history and dependency context.
Approach
From one seed domain, do what an attacker’s reconnaissance would — but deterministically and without payloads: discover the estate, fingerprint every endpoint at protocol level, build a trust graph, detect weaknesses, predict escalation, and give analysts a console with an attack simulator.
Principle
Same input, same output — always. Even retry jitter is derived from a hash, so every finding can be replayed for an auditor.
  • Discovery: 44 modules — 15 passive (CT logs, DNS, SAN chains, ASN/RDAP…) and 29 active/correlative (ports, TLS, crawl, JARM, CDN edges, cloud buckets, Kubernetes patterns…) — run explore-then-exploit under 30 s slices and hard caps (250K nodes, 500K edges).
  • Six analytical layers with enforced boundaries: L0 observation (24 fingerprints, 10 “physics” signals) → L1 trust graph (5 node types, 11 edge types) → L2 six weakness detectors → L3 bounded per-entity learning (EWMA, 90-day horizon, no wall clock) → L4 decision (8-phase campaign machine with hysteresis) → L5 React console + REST API.
  • Posture & compliance: TLS, certificate, HSTS, revocation, WAF and post-quantum findings mapped to PCI-DSS v4.0, RBI and NIST IR 8413; a 29-jurisdiction compliance catalogue.
  • Simulator: five attack scenarios re-run the pipeline in a sandbox and report blast radius, ranked paths and mitigations.
  • Engineering: stdlib-first Python 3.12 (three dependencies), PostgreSQL (17 tables) or an atomic filesystem store, cycle locks with heartbeat recovery, 271 tests including determinism suites, ~71K lines of Python and ~15K of TypeScript.
  • One demonstration cycle from a single seed domain: 184 related assets, 54/61 successful protocol observations, 46 TLS findings, 8 critical — in 6 minutes 43 seconds.
  • Trust graph of 960 nodes and 1,764 relationships; larger estates map 500+ endpoints in a ~10-minute cycle — work that takes a security team hours to days by hand.
  • Presented at IDBI Innovate 2026 (IDBI Bank hackathon) as a working console, not a concept.
  • Business development automated with an outreach agent that sourced 2,000+ leads and sent up to 200 personalised pitches a day.

“Chat with your PDFs” demos embed chunks, grab the nearest few and hope. They miss exact terms — product codes, clause numbers, names — and fail silently with a confident answer and no way to check it.
Approach
Treat retrieval as the product: two retrievers in parallel, principled fusion, explicit evidence selection and an abstention gate before any token is generated — then validate the citations after.
  • Ingestion: PyMuPDF with a fallback parser (8 formats, up to 50 MB); semantic chunking at 512 tokens with 64 overlap; one PostgreSQL database holds a tsvector GIN index and a vector(384) HNSW index.
  • Retrieval: lexical (ts_rank_cd) and dense (pgvector) each return 50; reciprocal-rank fusion (k = 60) to 25; dedupe, metadata, trust and freshness filters; re-rank to 10.
  • Generation guardrails: abstain unless ≥ 1 evidence item scores ≥ 0.3 with mean ≥ 0.4; grounding check ≥ 0.5; a citation validator; temperature 0.1.
  • Failover state machine: Gemini 2.5 Flash → GPT-4.1 mini → Claude Sonnet → Llama 3.3 70B (Groq); 3 retries with jittered backoff; 60–300 s cooldown after 3 failures.
  • Architecture: nine layers where imports only flow down; every component behind a typed interface; DATABASE_URL switches Postgres ↔ SQLite FTS5 + Qdrant; per-stage latency diagnostics; 160 tests, ~25K lines of Python.
  • Every answer is cited or withheld — the system says “not enough evidence” rather than guessing.
  • Deployed end to end: Next.js workspace on Cloudflare Pages, API on Koyeb, database on Neon; a public demo with a server-side 2-query trial.
  • The same hybrid idea, with a MiniLM transformer re-ranking BM25F + Word2Vec/FAISS candidates 50 → 10, powered my earlier PubMed search engine built for the Information Retrieval module.

EnergyNexus

Deep-learning forecasts of energy demand, electricity price and wind generation at 1, 6 and 24-hour horizons.

93.1%R² wind
70.3%R² price
Full case study Preview dissertation
Problem
Grid operators must balance supply and demand hourly while renewables make both sides harder to predict — and detailed city-scale energy data is locked behind regulation, privacy rules and corporate confidentiality.
Approach
Build three forecasters — demand, electricity price and wind generation at 1, 6 and 24-hour horizons — and test whether an architecture designed for one target transfers to another. Where real data was unavailable, design a synthetic London generator grounded in physical models.
  • Synthetic London data: 1,051,200 hourly rows × 125 features over 10 years and 12 boroughs — autoregressive weather, turbine power curves, de-rated solar, six demand sectors, and a price-formation model with a 26.4% coefficient of variation.
  • Demand model (830,963 parameters): three parallel Conv1D layers (kernels 3/7/15) → BiLSTM 112 → BiLSTM 84 → LSTM 112 with layer norm → 6-head attention with residual → pooled heads → three horizon outputs; Huber loss, Adam with gradient clipping, early stopping.
  • Price model: the demand architecture transferred with heavier dropout and a 0.7·Huber + 0.3·MAE loss.
  • Wind model (54,401 parameters): Daubechies-3 wavelet decomposition of real 2016 German ENTSO-E/OPSD data (wind speed at 2/10/50 m, roughness) → two-layer LSTM; evaluated on 1,307 held-out hours with MAE, RMSE, MAPE, index of agreement and residual diagnostics.
  • R² 95.9% on demand (95.7 / 96.8 / 95.1% by horizon; MAPE ≈ 4%), 93.1% on wind generation, 70.3% on price — all three dissertation objectives met.
  • Error analysis found the wind model over-estimates by ~15.5% in high-wind periods — a systematic bias that calibration could remove; documented honestly as a limitation.
  • MSc awarded with Distinction; the dissertation is available to read on this site.
